## 1. 证据等级与分数档位

- **使用方式**：`design-craft`，`critique` 模式；Surface mode = `Operate`。
- **证据等级：L0 static**——只有产品上下文和结构性文字描述，没有截图、DOM、computed style、token 实现或运行态证据。
- **概念层暂定档位：60–74 / 100，Functional but ordinary。**
- **判断置信度**：
  - 对信息架构、任务焦点和产品匹配度：中等。
  - 对排版、间距、色彩、组件质量和交互完成度：低。
- 这不是对已实现 UI 的精确视觉评分。即使实际页面制作得很整齐，`12 个等权 KPI + 装饰性图表 + 通用提示` 仍会限制其上限，因为核心问题是决策层级，而非视觉清洁度。

## 2. Design read

> Reading this as: 一个面向电商内部运营人员的、克制而高密度的 revenue-ops command center，优化目标是在下一小时内快速识别最高影响的账户或活动异常，并立即采取行动。

它应该首先回答：

1. **现在最需要处理谁？**
2. **为什么是它，影响多大，数据有多新？**
3. **下一步做什么，由谁负责，时限是什么？**

当前概念更像“经营数据总览”，而不是“小时级异常处置界面”。

## 3. Top hierarchy / product-fit issues

### B1 — P1：12 个等权 KPI 形成 `card soup`

等宽、等重的 KPI 把常规总量、异常信号和决策指标放在同一视觉层级。用户需要先阅读和解释指标，界面没有直接建立“哪个对象最值得处理”的优先顺序。

### B2 — P1：主要工作对象被概览内容压到下方

账户表很可能是实际处置入口，但它位于 KPI 和图表之后。即使表格本身可用，页面顺序仍让“查看概况”先于“发现并处理异常”，与下一小时决策任务相反。

### B3 — P1：装饰性面积图没有承担诊断职责

`Decorative` 已表明它不是围绕明确运营问题设计。面积图占据高价值空间，却没有被定义为解释异常、比较基线、展示阈值或帮助选择行动的证据。

### B4 — P1：通用 tips rail 缺乏对象、证据和责任闭环

通用提示既会与异常队列争夺注意力，也无法回答“针对哪个账户或活动、发生了什么、影响多少、下一步由谁做”。这属于 decoration disguised as insight。

### B5 — P1：概念未定义运营决策所需的上下文语法

当前描述没有说明时间范围、数据新鲜度、比较基线、异常阈值、收入影响、负责人、SLA 或下一动作。不能据此断言这些信息实际缺失，但在实现前必须把它们写入信息架构，否则排序和强调都没有可靠依据。

## 4. Concrete design moves

### M1 — 建立 `page command/context band`（解决 B5）

在页面顶部集中放置：

- 当前范围：Account / Campaign / 全部；
- 时间窗口和时区；
- 数据最后更新时间及 stale 状态；
- 当前过滤条件；
- 只看需要行动、未分配或临近 SLA 的快捷筛选。

保持紧凑，不做 marketing hero；它的职责是解释“我正在看什么数据”。

### M2 — 从等权网格改为 `lead + support + action queue`（解决 B1）

- 将一个真正影响优先级的状态作为 lead object，例如“当前收入风险”或“未来一小时需处理对象数”。
- 将少量辅助 KPI 收为紧凑 metric strip，而不是继续使用同权大卡片。
- 每个强调指标必须带上比较对象：相对上一周期、目标、阈值或正常基线。
- 其余低频指标移入详情、折叠区或二级分析页。

### M3 — 将异常队列／任务表提升到首屏主区域（解决 B2）

默认展示需要行动的账户或活动，而不是完整数据全集。排序逻辑应由已确认的数据语义决定，通常综合：

- 紧迫度或 SLA；
- 预估收入影响；
- 异常置信度；
- 是否已有负责人或处理状态。

用户应在约三秒内找到第一处理对象，并能解释其优先原因。

### M4 — 把表格改造成 `task-first table`（解决 B2、B5）

推荐首要列序：

`Identity → Severity/Status → Revenue impact → Observed change / threshold → Owner/SLA → Next action`

同时：

- 文本左对齐，金额、比率和数量右对齐并使用 tabular numerals；
- 筛选器贴近它影响的表格；
- 主标识、状态和行动在窄宽度下优先保留；
- 行动作使用明确的 verb-object 文案；
- 次要元数据后置、分组或按需展开，而不是按数据库字段顺序平铺。

### M5 — 将面积图改为 `diagnostic chart`，否则删除（解决 B3）

图表必须回答一个命名问题，例如：

- 哪个异常从何时开始？
- 当前表现相对正常区间偏离多少？
- 收入损失由哪些账户或活动贡献？
- 干预后趋势是否恢复？

使用比较基线、阈值、事件注释和直接标签；最好响应当前选中行或筛选条件。若无法改变用户的排序、诊断或行动，就不应占据主页面。

### M6 — 将 generic tips rail 改为 `context/action rail`，否则移除（解决 B4）

右栏只在能绑定当前对象时保留，内容应包括：

- 具体账户或活动；
- 触发条件和证据时间；
- 预估影响；
- 建议动作及其依据；
- 负责人、处理状态和审计记录。

如果这些信息无法获得，移除右栏，把宽度还给任务表。

### M7 — 使用 `enterprise dense + ops command center` 视觉处理

- 以平面分区、细分隔线和密度梯度代替大量浮起卡片；
- 最小化阴影、圆角层叠和装饰背景；
- 色彩只来自 token，并仅用于语义状态和可操作反馈；
- 高风险状态同时使用文字／图标／形状，不依赖颜色；
- 正文和表格保持紧凑，标题层级克制，数字对齐稳定；
- 高对比只留给异常、选中对象和主行动。

### M8 — 在编码前定义完整状态族和降级策略

至少覆盖：

- loading、empty、error、stale、permission denied；
- 无异常时的“系统正常”状态；
- 长账户名、极端金额、缺失值和大量行；
- hover、focus、selected、disabled 和 keyboard row action；
- 主桌面宽度与最小支持宽度下的列收缩、横向滚动和右栏处理；
- 图表 tooltip、legend 和标注溢出。

## 5. Verified versus unverified

### Prompt-established

- 产品是内部电商 revenue operations dashboard。
- 主用户需要决定未来一小时应关注哪个账户或活动。
- 当前概念包含 12 个等权 KPI、装饰性面积图、密集账户表和通用提示右栏。
- 目标风格是克制、密集但平静的 enterprise console。
- 色彩要求来自 tokens，不接受任意装饰色。
- 本轮仅进行了基于描述的结构性 critique。

### Unverified

- 页面实际是否整洁、对齐或具有一致 spacing rhythm。
- 字体、字号、数字对齐、边框、圆角、阴影和 token 是否真实合规。
- KPI 是否已有周期、基线、阈值、tooltip 或 drill-down。
- 表格实际列序、排序、筛选、固定列、行操作和数据质量。
- 图表比例尺、标签、legend、tooltip、零基线和数据准确性。
- 右栏是否可能根据当前账户动态变化。
- hover、focus、selected、loading、empty、error、stale 和 permission 状态。
- 键盘、屏幕阅读器、对比度和非颜色状态表达。
- 响应式、窄屏、长文本、极端数值和真实数据量表现。
- 本轮**没有进行浏览器、DOM、截图或交互验证，也没有修改文件**。

## 6. 实现前的最小验证计划

1. **取得真实 baseline**  
   收集主工作视口的整页和首屏截图、实际 DOM／token 证据、当前表格列定义，以及一组去敏的真实数据样本。

2. **确认决策数据合同**  
   与运营负责人确认指标定义、数据延迟、比较基线、异常阈值、收入影响算法、负责人和可执行动作；没有这些语义，不应先设计排序和强调色。

3. **用真实任务验证信息优先级**  
   选择至少三个代表性场景，让 2–3 名目标运营人员回答“先处理谁、为什么、下一步是什么”，记录定位时间、误判和缺失信息。

4. **先验证低保真决策流**  
   测试 `command band + lead/support + exception queue + diagnostic chart` 的线框版本。最低通过条件是用户能迅速找到同一个最高优先级对象，并能从界面证据解释选择。

5. **锁定实现验收矩阵**  
   明确主桌面与最小支持宽度，以及 loading、empty、error、stale、permission、长文本、极端数值、keyboard focus 和 chart overflow 检查项。实现后仍需真实浏览器和截图复核；本轮未执行这些验证。
