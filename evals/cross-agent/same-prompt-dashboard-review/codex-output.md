# Dashboard 概念评审

## 1. 证据等级与评分区间

- **实际使用**：`design-craft`，模式为只读 `critique`。
- **证据等级：L0 static**。只有文字描述；虽然提供了产品、用户和任务背景，但没有截图，因此尚不满足需要截图支撑的 L1。
- **样式权威**：仅采用提示中的“克制的企业控制台、密而不乱、无营销 Hero、颜色全部来自 token”。
- **暂定 Product UI taste score：60–74 / 100**
- **档位：Functional but ordinary**
- 这是**概念结构评分**，不是对实际渲染质量的评分。现有模块大致覆盖概览、趋势和明细，但没有围绕“一小时内先处理什么”建立明确的决策顺序。
- 即使后续截图证明视觉执行整洁，只要 `card soup`、装饰性图表和扁平优先级仍存在，评分也不应超过 84。
- Route planner 未运行：本次是 L0 只读评审，不是 L1+ 实现任务。
- 未进行浏览器、DOM、响应式或原生验证；没有截图或运行态 artifact。

## 2. Design read

**Reading this as：一个面向电商营收运营人员的克制型 `Operate` 控制台，采用 `enterprise dense + ops command center` 语法，优化目标是快速识别最高影响、可执行的账户或活动异常，并立即采取下一步行动，而不是平铺展示十二个指标。**

核心工作不是“看数据”，而是完成以下决策链：

1. 现在最需要关注哪个账户或活动？
2. 为什么是它，异常依据和影响是什么？
3. 数据是否新鲜、结论是否可信？
4. 下一步动作是什么，由谁负责？
5. 执行动作后去哪里确认结果？

## 3. 阻塞性的层级与产品适配问题

### P1-1：十二张等权 KPI 卡造成 `card soup`

相同尺寸和表面权重会把例行总量、健康指标和紧急异常处理成同一优先级。用户必须逐卡阅读并自行综合，界面没有替用户控制注意力。

### P1-2：缺少明确的 `decision surface`

描述中没有 `lead risk object`、异常队列或下一步行动层。当前结构回答“发生了什么”，但没有直接回答“下一小时先处理什么”。

### P1-3：装饰性面积图消耗了错误的视觉预算

图表没有被描述为回答某个运营问题，也没有阈值、对照、异常注释或与具体对象的连接。它占据焦点，却不能支持判断，属于 decoration disguised as evidence。

### P1-4：密集表格尚未体现 `task-first table` 结构

密度本身不是问题；企业运营台需要密度。问题是没有证据表明账户身份、状态、风险、营收影响、异常原因和下一动作位于扫描路径前端。若表格排在装饰图表之后，它作为主要工作对象的层级也过低。

### P1-5：通用 tips 右栏与当前决策脱节

固定右栏占用高价值横向空间，却没有绑定具体账户、触发阈值、业务影响、数据时间、负责人或操作。它既不是解释，也不是行动队列，会制造“系统很聪明但没有帮助”的 generic AI tell。

## 4. 八个具体设计动作

1. **建立紧凑的 command/context band。**  
   顶部只放当前范围、账户/活动视图切换、时间窗口、数据刷新时间、核心筛选和必要操作。不要做 Hero；让用户始终知道“正在看什么、截至何时、筛选了什么”。

2. **将十二张等权卡改为 `lead + support` 层级。**  
   用一个主导对象表达“当前最高优先级异常”或“可执行营收风险”，其余只保留能改变优先顺序的 4–6 个紧凑支持指标。每个强调值必须带周期、对照或阈值，并显示数据新鲜度。

3. **在首屏建立 `exception/action queue`。**  
   按已确认的业务规则排序，例如业务影响、紧急度、置信度和可执行性；每项显示对象类型、名称、触发原因、预计影响、异常持续时间、负责人和明确的 `verb + object` 下一动作。不要只按异常幅度排序。

4. **把面积图降级为 contextual diagnostic chart，或删除。**  
   图表必须回答一个命名问题，例如“该活动何时开始偏离目标节奏？”；提供目标/基线、阈值、时间范围、直接标注和异常点，并与当前选中的队列项联动。若没有明确问题，就把空间让给队列或表格。

5. **删除 generic tips，或改成上下文行动栏。**  
   仅在内容能够明确给出“对象 + 触发依据 + 影响 + 建议动作 + owner + timestamp”时保留。否则取消固定右栏，让表格获得宽度；次要解释可进入选中行的 drawer。

6. **将账户表改造成 `task-first table`。**  
   推荐扫描顺序为：对象身份 → 状态/风险 → 营收影响 → 关键变化 → 数据时间 → owner → 下一动作。文本左对齐、数字右对齐并使用 tabular numerals；次要元数据后置或按需展开，筛选和排序紧邻表格。

7. **建立克制但明确的语义视觉系统。**  
   使用 token roles 管理 `surface`、`text`、`border`、`focus-ring` 和状态色；颜色只表达状态，不装饰模块。默认采用细分隔线、最少 elevation、紧凑字号和清楚的 `density gradient`；异常同时使用文字、图标或形状，不能只靠颜色。

8. **把韧性、可访问性和窄宽度行为写入组件合同。**  
   覆盖 loading、empty、error、stale、partial-data、permission 和 long-content；定义键盘焦点、行选择、排序状态、tooltip 和恢复动作。窄宽度下优先保留对象、风险、影响和动作，而不是机械地把桌面模块纵向堆叠。

## 5. 已验证与未验证

### 已知，但仅来自提示文本

- 产品是内部电商 revenue operations dashboard。
- 主要用户需要决定下一小时关注哪个账户或活动。
- 当前概念包含十二张等权 KPI 卡、装饰性面积图、密集账户表和通用 tips 右栏。
- 目标风格是克制、密而不乱的企业控制台，并要求颜色 token 化。
- 基于上述结构，扁平优先级与任务目标之间存在明确的概念错配。

这些是**brief-level facts**，不是对实际产品运行态的验证。

### 未验证

- 实际截图、首屏构图、模块尺寸、间距、对齐轴、字体层级和信息密度。
- 颜色是否真的来自 token，以及对比度、暗色主题或状态色是否合规。
- KPI 的真实定义、时间范围、比较基准、刷新频率和数据可信度。
- 异常排序规则、阈值、影响估算和账户/活动之间是否可以直接比较。
- 表格列顺序、排序、筛选、分页、sticky 行为、行操作和横向溢出。
- 图表比例尺、基线、图例、tooltip、数据缺口和响应式行为。
- hover、focus、active、selected、disabled 和键盘操作。
- loading、empty、error、stale、partial-data、permission 等状态。
- 长名称、大数字、无异常、大量行、窄视口、缩放和辅助技术行为。
- 实际运营人员是否能更快、更准确地识别首要行动。
- **本轮没有进行任何浏览器验证。**

## 6. 实现前的最小验证计划

1. **确认决策合同。**  
   与至少一名实际运营人员和一名数据口径负责人确认：优先级如何计算、什么属于可执行异常、数据多旧会失效、可采取哪些动作、账户与活动是否需要分视图。

2. **取得基线证据。**  
   若已有界面，采集一个主要桌面宽度和最小支持宽度的完整截图，并记录模块顺序、真实数据样例、表格字段和 token；若尚无界面，则提供等价的带内容线框图。不要只使用理想化短文本。

3. **准备最小状态样本。**  
   至少包含：正常数据、多个高风险对象、无异常、陈旧/部分数据、请求失败、长账户名、大数字和高行数。先用这些样本检查信息架构，再确定组件尺寸。

4. **用低保真 `lead + support + action queue` 原型做任务测试。**  
   让 2–3 名代表性运营人员完成“找出第一优先对象、解释原因、选择下一动作”。暂定验收目标：3 秒内找到首要对象，10 秒内说出依据和影响，且无需在十二个 KPI 之间人工拼接结论。

5. **在编码前锁定实现后的验证矩阵。**  
   约定需要检查的视口、200% zoom、键盘路径、focus-visible、状态族、表格溢出和图表 tooltip；实现后再执行 type/lint/build、真实浏览器 smoke、截图对比和 DOM/computed-token 检查。当前评审不把这些计划项表述为已通过。
