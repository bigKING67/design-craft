## 1. 证据等级与评分带

- **Selected skill / mode**：`design-craft` / `critique`
- **Surface mode**：`Operate`
- **平台判断**：内部 Web/桌面控制台；由产品描述推断，未由源码或运行态确认。
- **证据等级**：**L0 static**。只有概念文字描述；虽然提供了用户和任务上下文，但没有截图，因此不满足 L1 contextual。
- **暂定 Product UI taste score band**：**60–74 / 100，Functional but ordinary**。
- 该评分只评价已描述的**信息架构、任务聚焦和产品匹配度**，不是对实际排版、颜色、响应式或交互质量的评分。
- 不给出更精确分数：当前证据不足以判断视觉执行质量；但“12 张等权 KPI 卡片 + 装饰性图表 + 通用提示”已足以把概念限制在 75 分以下。
- 正向条件是：产品风格目标正确，密集账户表也可能成为有效工作对象；主要扣分来自决策层级，而不是“看起来不够高级”。

**一句话诊断**：当前方案更像等权展示经营数据的汇总页，而不是帮助运营在一小时内发现、解释并处置最高优先级异常的 revenue-ops 决策面。

## 2. Design read

**Reading this as：面向内部电商运营的克制、精确、企业级 revenue-ops command surface，优化目标是在数秒内识别最需要干预的账户或活动，并立即理解原因、影响和下一步动作。**

它应优先支持四步闭环：

1. **Detect**：哪个账户或活动现在异常。
2. **Understand**：相对什么基线异常，影响有多大，数据是否新鲜。
3. **Act**：运营应该执行、分配或升级什么动作。
4. **Confirm**：动作是否被接收，问题是否仍在持续。

因此，首屏应是 **decision surface / exception queue**，而不是 executive summary，也不应通过更大的数字、更多卡片或营销式视觉制造“重点”。

## 3. 最主要的产品与层级问题

以下均按 **P1 概念门禁问题**处理；L0 证据不足以将其上调为运行态 P0。

1. **Flat priority / card soup**
   - 12 张等权 KPI 卡片让所有指标同时争夺注意力。
   - 运营仍需自行完成“哪个指标重要、哪个实体受影响、是否需要现在处理”的解释工作。
   - 等权网格表达的是指标目录，而不是优先级。

2. **信息顺序与用户决策顺序相反**
   - 装饰性面积图位于密集账户表之前，而账户或活动才是可以被处置的工作对象。
   - 页面当前是“摘要 → 图表 → 工作对象”，更合理的顺序应是“异常对象 → 影响与动作 → 诊断证据 → 全量明细”。

3. **表格可能是 data dump，而不是 task-first table**
   - 提示只证明表格“密集”，没有证明它把 `identity / status / risk / impact / owner / next action` 放在扫描路径前部。
   - 也未说明默认排序、异常筛选、行级动作、升级路径或动作反馈。
   - 密度本身不是问题；没有决策顺序的密度才是负担。

4. **图表和右栏都缺少决策职责**
   - “装饰性面积图”没有命名分析问题、比较基线、阈值、异常标注或下钻路径。
   - “通用提示”没有实体、观测变化、业务影响、负责人和下一动作，属于 decoration disguised as analysis。
   - 两者共同占用了本应属于异常队列和行动上下文的注意力。

5. **运营解释与信任合同未在概念中建立**
   - 概念没有说明 KPI 的时间窗口、比较口径、异常阈值、数据更新时间、同步状态、归属人或 SLA。
   - 这些不能据此断言实际页面一定缺失，但在进入实现前必须明确；否则数字无法支持安全的即时决策。

## 4. 八个具体设计动作

1. **建立 page command/context band**
   - 顶部固定表达：业务范围、当前时间窗口、比较基线、最后更新时间、同步/部分失败状态和生效中的全局筛选。
   - 筛选器靠近其影响的数据，不要分散到无关工具栏。
   - 页面标题建议使用项目 token 对应的约 24px 角色；时间、更新状态等元数据使用 12–13px，保持可读对比度。

2. **把等权 KPI 网格改成 `lead + support + action queue`**
   - Lead 不应只是“最大的收入数字”，而应是当前排名第一的异常对象或异常队列摘要。
   - 从 12 个 KPI 中保留约 4–6 个真正会改变本小时动作的 supporting metrics；其余进入诊断层或详情。
   - 每个重点指标必须回答“相对什么”：上一小时、同周期、目标、阈值或计划值。
   - 数字采用 tabular numerals；状态颜色只表达语义，不用于装饰。

3. **把异常队列和 task-first table 提到首屏主区**
   - 默认依据经业务确认的 `urgency × impact × confidence` 或现有规则排序，不由视觉层私自发明优先级算法。
   - 前置列建议为：账户/活动、状态或风险、收入影响、触发原因、负责人/SLA、下一动作。
   - 次级元数据分组到后部或行详情；数字右对齐、文本左对齐。
   - 决策性表格正文以 **14px / 1.4** 为无更强项目规范时的暂定下限，12–13px 仅用于次级元数据。
   - 行动作必须明确、可键盘到达，并在操作后显示成功、失败或处理中反馈。

4. **把面积图降级为 diagnostic evidence，不能证明价值就删除**
   - 图表必须回答一个命名问题，例如：“哪些活动在最近一小时显著偏离基线？”
   - 同时呈现当前值、比较值、阈值/目标和异常点，并能筛选或下钻到对应表格行。
   - 优先使用直接标签和语义 token；避免只靠面积填充和颜色传递状态。
   - 若图表不会改变用户的排序、判断或动作，则删除，不用另一种图表替换装饰。

5. **删除通用 tips，或改为上下文 action panel**
   - 右栏可绑定当前选中账户/活动，展示：实体、观测变化或阈值、预计影响、紧迫度、负责人、建议动作和直达入口。
   - 如果这些信息已经由异常队列和行详情承担，就直接移除右栏，避免重复 cardification。
   - 不接受“关注转化率”“建议优化投放”之类无法定位实体和动作的泛化文案。

6. **采用 `enterprise dense` 的克制视觉语法**
   - 默认使用平面内容区和 subtle divider，不给每个指标单独加阴影、重边框或强背景。
   - Elevation 只保留给 popover、drawer、modal 等真实层级；普通内容依靠分组、留白和排版建立结构。
   - 建议使用项目 token 映射的 8/12px 紧密关系、16px 组件间距、24px 分组间距。
   - 颜色只来自 token；危险、警告、成功、信息状态同时配合文字或图标，不使用 color-only distinction。
   - 决策文本满足 WCAG normal-text contrast；不要通过降低关键文字对比度换取“安静感”。

7. **把状态族写入组件合同**
   - Loading：保留页面上下文和表格列宽，明确正在加载哪个时间范围。
   - Empty：区分“确实没有异常”和“筛选后无结果”，提供清除筛选或返回全量数据的动作。
   - Error：错误局部呈现，保留时间范围和筛选上下文，提供明确重试。
   - Partial/stale：展示最后成功更新时间、缺失范围和影响模块，禁止把旧数据伪装成正常实时数据。
   - Permission/disabled：解释不可操作原因和申请或升级路径。

8. **为窄屏、键盘和辅助技术定义降级方式**
   - 在项目确认的最小支持宽度下，Lead、最高优先级对象和主动作仍须首先可见。
   - 将不可避免的横向滚动限制在表格数据区；页面级动作和筛选不能被推出视口。
   - 右栏在窄宽度下转为行详情/drawer 或移到主内容之后，而不是简单压缩。
   - 定义 `focus-visible`、逻辑 Tab 顺序、非颜色状态标识、图表文本摘要或等价数据表，以及 tooltip 的键盘访问方式。

## 5. 已证实与未证实

**由本提示建立、仅在 L0 范围内成立：**

- 产品是内部电商 revenue-operations dashboard。
- 主要用户要在下一小时决定关注哪个账户或活动。
- 概念包含 12 张等权 KPI 卡、装饰性面积图、密集账户表和通用 tips 右栏。
- 风格权威要求克制的企业控制台、密集但平静、无 marketing hero、仅使用 token-backed color。
- 本轮没有截图、DOM、运行态或交互状态证据。

**未验证，不能作为当前页面事实宣称：**

- 实际视觉层级、间距、字号、对齐、颜色、对比度、边框、阴影和 token 使用。
- KPI 的业务口径、比较周期、异常阈值、排序逻辑和数据新鲜度。
- 表格列顺序、筛选/排序、行级动作、长文本、高行数和水平溢出行为。
- 图表的比例尺、标签、tooltip、异常标记、可访问性和数据正确性。
- Hover、focus、keyboard、loading、empty、error、partial、permission、success 状态。
- 响应式表现、真实内容表现、性能和辅助技术体验。
- **文件改动：无。浏览器验证：未执行。**

## 6. 实现前的最小验证计划

以下是计划，不是本轮已执行证据：

1. **确认决策真相**
   - 与 2–3 名实际运营复盘至少 3 个近期典型事件。
   - 对每个事件确认：正确优先对象、触发信号、业务影响、时间要求、负责人和下一动作。
   - 明确排序规则由什么业务口径决定。

2. **建立当前基线**
   - 获取当前页面在主要桌面宽度和项目最小支持宽度下的截图。
   - 检查 DOM/computed style/token 来源、实际表格列与动作、图表语义和数据更新时间。
   - 这一步完成后，基线证据才可提升到 L2；本轮没有完成。

3. **准备代表性数据与状态**
   - 至少覆盖：正常、单个高风险、多异常、长名称、高数值、无异常、筛选无结果、loading、局部 error、partial/stale。
   - 为每个状态写清楚“渲染什么、用户能做什么、保留什么上下文、如何恢复”。

4. **用低保真 decision-surface 原型做任务验证**
   - 使用真实语义但脱敏的数据，测试“找出最需要处理的对象并发起正确动作”。
   - 最小通过门槛：用户约 3 秒内定位最高优先级对象，能够说明异常依据和影响，并能直接找到下一动作。
   - 同时评审最小宽度布局、表格降级、非颜色状态语义以及预期 Tab 顺序。

5. **实现门禁**
   - 只有在优先级规则、首屏信息顺序、表格列合同、图表职责、状态恢复和 token 映射获得确认后，再进入代码实现。
   - 实现后的浏览器、响应式、焦点、状态和真实数据验证仍是发布门禁，不能由本次概念评审替代。
